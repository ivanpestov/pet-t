# Слоистая архитектура и границы тестирования

Монолитный бинарник Таймера разделяется на библиотеку и тонкий бинарник
`t`, чтобы отделить доменные правила и оркестрацию от инфраструктуры.
Правило зависимостей и границы тестирования фиксируются явно, поскольку
их нельзя сохранить одной структурой каталогов.

## Решение

- Зависимости направлены от `adapters` к `application` и от `application`
  к `domain`. Бинарник знает все слои и выполняет только композицию,
  вызов разбора аргументов и отображение исхода в код выхода.
- Порты находятся только на границах ввода-вывода. Домен не зависит от
  файлов, системных команд, D-Bus и обработки Ctrl+C.
- Библиотека остаётся внутренним API бинарника. Пакет не разделяется на
  workspace, новые зависимости не добавляются.
- Модули оформляются файлами `<модуль>.rs` рядом с одноимёнными
  директориями без `mod.rs`.
- Используются три seam: процессные integration-тесты, unit-тесты
  чистого домена и in-process тесты application с фейками портов.
  Решение предыдущих specs «единственный seam — процесс» отменяется для
  домена и application.

## Рассмотренные альтернативы

- Сохранение монолита оставляет доменные правила связанными с процессом,
  реальным временем и системными вызовами.
- Несколько крейтов или workspace добавляют структурную сложность без
  необходимой для этого пакета изоляции.
- Только процессные тесты сохраняют минутные ожидания и не дают быстро
  проверить ветки оркестрации и ошибок.
- Абстракция монотонного времени не вводится: события application можно
  подавать синтетически, а естественное завершение проверять с нулевой
  длительностью непосредственного вызова сценария.

## Последствия

Домен и application получают быстрые тесты, а конкретные адаптеры
остаются проверяемыми через процессный контракт. Новая фича может
затрагивать несколько слоёв, но направление зависимостей и владение
правилами не меняются. Конкретные адаптеры in-process не тестируются.
